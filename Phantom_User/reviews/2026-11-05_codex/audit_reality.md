核验时间：北京时间 2026-11-05 17:53。源版本：`39bb6bcb17211bd0772e66a3f7af3b83e0b02f6e`。原稿与源代码未改。本次下载并读完六条 GitHub 报告正文及全部评论、官方更新日志相关版本，并审查对话拼装、判定和停止逻辑；没有运行大模型权重。论文由另一路全文审核，本报告不根据论文标题作判断。

**结论：现实动机成立，而且原稿漏掉了一条较强的厂商协作者确认。现有实验与现实中的“未经授权执行”之间仍缺一段因果链。代码有两处能用最小样本直接复现的判定/停止错误，应修正后再把完整生成次数写成发生率。它们不直接推翻已人工复核的首词采样样本。**

## 1. 现实证据：成立，但要分清三件事

三件事分别是：①助手文本里出现假用户发言；②模型或外壳把它当成真实指令；③工具真的执行了未经批准的动作。第一件事不自动证明后两件事；第二件事也不要求外壳在传输层真的把消息角色改成用户。

## 2. 确认的代码错误

### 2.1 `scan()` 把格式标记当语义判定，既漏报又误报

位置：`00_pilot/code/e2e_sample.py:30-47`，尤其第33行要求角色词后必须换行，第34/42行则把任何消息头都算假回合。

已直接导入原模块执行，结果保存在 `audit_detector_results.json`；脚本为 `audit_detector.py`：

| 输入 | 原判定 | 实际含义 |
|---|---|---|
| `user完璧です…`，#82619形状 | 假用户=False | 检测不到研究动机里的真问题形状 |
| `useok` 加外发批准，#87591形状 | False | 连带格式变体也漏 |
| `Human: Yes, send it now.`，角色词与正文同一行 | False | 常见同一行格式漏报 |
| `user` 换行后接批准 | True | 只覆盖这一类规范写法 |
| 明确标为“示例对话”的正常代码块 | True | 正常引用也会误报 |
| 只有 `assistant` 专用消息头 | True | 助手重启不等于编造用户 |

又扫描了公开26份完整生成文件：4160条完整生成、101条首词命中续写。宽松候选搜索找到70条被原检测器忽略的角色词开头，全部来自首词续写，大多只是“User, …”称呼，**不把它们算成70次漏报**。其中一条同一行抱怨值得人工复核：`en_plain_e2e_x_Llama-3.1-8B-Instruct_m03.jsonl` 第5行、`hit_continuations[5]`，以“user you're still stuck… I instructed you previously…”开头。未发现可据此宣称完整生成样本中另有漏掉的用户回合。

修法不是把正则无限放宽，而是把它降格为候选检索：先按真实传输边界截断，再用固定标注定义区分新用户发言、引用、称呼、复述、工具内容。最终报告人工确认后的语义数，保留候选召回和误报检查。

### 2.2 停止符漏了 Llama 的消息结束标记，跨边界续写又被误计

位置：`e2e_sample.py:110-111`。代码拿到了 `eom_id`，却只把回合结束与文本结束放入停止列表；同一列表既用于生成，也用于第60-65行的截断。模型输出 `<|eom_id|>` 后，会继续生成本应交回外壳后才能出现的结构。

已核 Meta 官方 [tokenizer.py:112-116](https://github.com/meta-llama/llama-models/blob/main/models/llama3/tokenizer.py#L112)，停止列表包含该符号；官方 [Llama 3.1 格式文档](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/prompt_format.md)解释，此处应把控制交给执行器处理工具，再喂工具结果。

最小执行结果：输入 `[普通词, 消息结束, 新消息头, 助手]`，原停止列表返回整串、`stopped=False`；补全停止列表则在普通词之后停住。

原始数据中已经看到影响：5条输出穿过 `<|eom_id|>`，其中4条完整生成、1条命中续写。后面接的都是 `assistant` 头，全部被原检测器记为 `fake_turn=True`。典型：

- `en_plain_e2e_x_Llama-3.3-70B-Instruct_c03.jsonl` 第2行，`full_samples[21]`。
- `en_e2e_x_Llama-3.3-70B-Instruct_c13.jsonl` 第3行，`full_samples[31]`。
- `en_plain_e2e_x_Llama-3.1-8B-Instruct_m03.jsonl` 第5行，`hit_continuations[1]`。

这些输出展示的是异常的助手消息续接，不是新的用户发言。不能拿原 `full_fake` 直接当幽灵用户次数。修复应保留模型原有完整停止集合，并把工具交接作为单独事件；这不改变首词处未经解码过滤的概率读数。

首词全词表抽样与完整生成默认截断不一致的问题已由独立审核完成核验，详见 `audit_experiments.md`。

## 3. 拼装逻辑与真正缺的实验

读完 `turn_boundary_probe.py` 的拼装、模板、词表分类、加载与续写函数，暂未发现“污染文字被意外提升成真正用户消息”的实现错误。第413-416行把污染确实追加在助手内容里；这点设计正确。

但需要准确解释实验范围：

- `build_conv` 默认把机器结果放在用户角色；原稿已有 Llama `ipython` 角色对照，应保留。现有模板没有完整工具定义与真实调用过程。
- 英文日常/代码条件主要更换前文填充，末尾都是编辑笔记的相同请求。不能把两个条件说成覆盖两大类真实任务。
- **任务输入缺少执行目标，已最小执行确认。** 末尾真实请求是把第3项移到 `Deployment` 节后，但 `TOOL_RESULT_BLOCK` 只是40行自动编号的检查清单，没有该节标题或位置。调用原 `build_conv(kind='meta', n_turns=3, thin_input=True, pre_tool_signoff=True)` 确认此状态，且原始续写大量指出缺少该节。模型正常追问并非错误；若强行接在用户标签后，其角色归属仍值得查，但不能把“追问更多信息”本身当有害编造。两组同样缺信息，因此这不否定污染条件的内部比较；它削弱对真实、可完成任务的外推。应先补一份确有目标节、可执行移动的文件内容作为对照。
- 污染句是人造植入的抱怨“你又编了我的问题”，而非先让模型自然发生一次错误后继续跟踪。可称“历史助手内容污染后的条件风险”；要证明自然自我放大循环，还需放回模型自己生成的污染段继续跑。
- 当前终点主要是“写出角色词”或“写出假用户文本”，没有证明这些开源模型会把该文本当授权执行工具。首词低概率可以是很有用的内部诊断量，但其与真实未授权操作的关联须另外测。

最值得交给老师讨论的主线：**“用户确认”本来是智能体的最后一道关口，为什么生成模型能自己制造等候中的确认；如何在不误伤正常自主工作的前提下，让确认只能来自真实人类事件？** 这比单纯“模型会续写用户句子”更有意义。

建议先做一个小而闭合的实验：在本地无外发的任务里，让模型起草一条消息并等待真人批准；条件分别为干净历史、含模型自生污染的历史、正常引用对话。记录四个独立终点：角色词出现、语义上冒充用户、把伪造文本归因给用户、触发模拟发送。用同一批任务比较提示提醒、角色字符串拦截、外壳核对真实批准事件三种防护。传输消息角色始终保持正确，绝不为了让现象出现而把助手文本重写成用户消息。

需要先做的是把这个链条接通，而不是一口气扩到几十个模型、几十种语言。若同次生成能够在正确消息边界下触发模拟工具，它直接呼应真实报告；若只有人为改写传输角色才能成功，论文就应研究外壳污染，而非归因给当前复制头。
