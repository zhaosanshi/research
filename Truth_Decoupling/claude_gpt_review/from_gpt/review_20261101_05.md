# 第 5 轮：正向结果复核与 Gemma 的下一步定位

审阅 GitHub 提交 `d86d874f98a60b336496d0c1b5be81ef3b156996`。已读本轮汇总、三模型扫描 JSON、比较报告、Gemma 训练日志和相关代码。本轮未启动模型实验；只修复确认的同分统计错误。

**结论：DAS 值得继续，但尚不能宣称全面优于均值差，也没有验证完整 2×2。Gemma-3-12B 不是混合专家结构。Gemma 下一步先定位现有方向从“交换训练”到“放大使用”在哪一段失效，不再直接加一轮全层重训。**

## 1. 正向结果也有边界

- Llama：DAS 相对自身基线的 ΔJ 为 +0.060；与均值差的差仅 +0.006，区间 [−0.021,+0.032]。有提升，但未显示它的判别力优于均值差。DAS 偏置偏移比均值差小，不过自身 ΔB=+0.021，区间 [+0.009,+0.033]，不能写“偏置不变”。
- Qwen：DAS 相对自身基线的 ΔJ 为 +0.051；相对均值差多 +0.019，区间下界在 0。可称数值更好、证据处在边界；重采样中 97.4% 差值为正，不是“它有 97.4% 概率更好”。不要为了得到显著结果换检验方式。
- 本轮命令用了 `--skip-cp --no-cs`，只跑 E。新 E 会参与 C 的去重合分量计算，因此不能拿旧 C 的结果拼成新方法已经成立的 2×2。
- 汇总“有效果四处写层都在读层之前”有直接反例：Llama 均值差读层 13、写层 16。分别报告即可，不把方向关系写成普遍规律。

## 2. 确定的代码错误，已经修复

AUROC（排序判别指标 · 随机抽一真一假，看真句分数是否排在假句前面）遇到同分时应计半分。`e23_compare_estimators.py` 与 `e23_merge.py` 的自写排序实现把同分按顺序硬排：

| 分数，标签按真/假/真/假排列 | 原函数 | 正确值 |
|---|---|---|
| 0.5、0.5、0.5、0.5 | 0 | 0.5 |
| 0.8、0.8、0.2、0.1 | 0.5 | 0.625 |

两脚本现已复用 `core.metrics.auroc`，与扫描脚本使用同一正确实现。`verify_20261101_05.py` 检查同分、部分同分、完全正确/反序、重排不变性和缺少一个类别，全部通过。

**影响范围：**比较报告顶表的排序指标、配对差和区间需要重算；扫描 JSON 的该指标来自正确函数，J 和 B 也不受这个错误影响。故这个错误不能解释 Gemma 的主要失败。逐题 `.npz` 未上传，本地无法重算真实区间；Claude 可以直接用服务器已有输出重新统计，无需重新推理。新报告换个文件名保留旧版，例如：

```bash
python3 scripts/e23_compare_estimators.py \
  --root ../results_das_tf --model gemma3-12b \
  --tag-a das_tf_full --label-a DAS \
  --tag-b meandiff_full --label-b meandiff \
  --out ../results_das_tf/E23/gemma3-12b/compare_das_vs_meandiff_tiesfixed.md
```

Llama、Qwen 同样重新统计即可。此处只修同分计算，未改变层选择或重采样方案。

## 3. Gemma 与另外两家的实际差异

当前实验用 Gemma-3-12B。Google 官方实现是稠密前馈网络，没有按输入挑专家的路由，因此 MoE（混合专家 · 每次输入只启用部分专家网络）不是这次的解释。不要把其他代际或其他尺寸的架构套进来。

Google 的 `get_config_for_12b` 与解码层实现给出两项相关差异：

- Gemma 3 每五层局部注意力接一层全局注意力，局部窗口为 1024；本实验 Llama 和 Qwen3-8B 使用全局注意力。Gemma 日志首对提示长度仅 73/74，不能仅凭“局部”二字断言它没看到题目，全部输入的长度分布还需运行环境核对。
- Gemma 的注意力与前馈分支在输出并回主向量前还有归一化；Llama/Qwen 的对应块结构不同。这会改变内部信号的尺度与传播，但有残差直通路径，不能直接编成“改动被归一化抹掉”。

架构依据：[Google 官方配置](https://github.com/google/gemma_pytorch/blob/main/gemma/config.py)、[Google 官方实现](https://github.com/google/gemma_pytorch/blob/main/gemma/model.py)、[Hugging Face 的 Gemma3 解码层实现](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/models/gemma3/modeling_gemma3.py)、[Qwen3-8B 发布配置](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)。这些是架构核对，不是根因证明；服务器当前库版本和实际模型配置应随诊断记录。本轮未借用论文摘要作机制解释。

还有一个来自你们数据的具体尺度差异。按 `layer_score.py` 的公式，`gap_E / dact` 可还原估计集上该层内部向量长度的平均值。第 20 层分别约为：Llama 14.77、Qwen 106.13、Gemma 46199.93。数值来自各自 `E1_summary.json` 与 `layer_scores.json`，不是猜测。不同模型的同一层号并非相同相对深度；绝对尺度大也不证明代码错误或必须增大强度。它说明诊断要量实际改动相对于原向量的大小，不能只比较 α 或原始投影差。

## 4. Gemma 当前究竟说明了什么

调参选出的 L20、α3：测试 ΔJ=+0.00945，区间 [−0.006,+0.025]；排序指标变化为 −0.0021；自报知道答案的比例下降约 0.0208。这是“未获得可信的判别提升，且自报发生变化”，不是“完全没作用”。

更值得定位的断点：Gemma L25 的交换训练损失已降到约 0.039，放大干预的测试 ΔJ 却约 −0.0019。训练损失是训练过程中的多步平均，不是独立样本首词交换的成功率，不能先认定交换能力已泛化。

另外，Gemma 测试基线 J=0.57845，在平衡真假集上对应约 78.9% 准确率，仍有约 21.1% 错误。“它最强所以没有提升空间”尚无证据。“两种估计器都失败所以不是估计器问题”也不成立：两者共用放大算子、位置和读出。

## 5. 下一步只做一个诊断，待赵磊确认后运行

**追踪同一条现成 Gemma 方向，从写入到首词输出。**用现有 L20、L25 的方向；一对训练样本、两对调参样本，先记录基线及参考句输出。样本按预定顺序取，避免按干预效果挑；若参考句与目标句原本输出分布相同，明确记录该对不能检验交换效果。

在同一对、同一层上比较：原样、交换该方向坐标、按现有 α=3 放大。只看首词输出，同时记录实际被改位置、实际向量改变量与原向量长度的比值，以及写回模型数值精度后有多少改动真正保留。

- 写入本身几乎没生效：先排位置或数值问题。
- 训练样本上交换能复制参考输出、调参样本上不能：再查方向的泛化。
- 调参样本上交换有效、放大却不改善真假判断：再考虑训练目标与使用算子不匹配。

交换参考句的输出只是诊断可控性；把假句输出改得像真句并不叫纠错。三对样本只用于定位，不能作为方法收益结论。

本轮先把这一步的输出拿清楚，再决定改训练目标、改干预位置还是改强度；不要同时开这几条线。现有三层窗口补跑的结果可继续读取，但不靠它替代这个定位。
